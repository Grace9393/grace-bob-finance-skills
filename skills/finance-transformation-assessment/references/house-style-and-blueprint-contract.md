# House Style and the Blueprint Contract

This skill operates inside an existing practice asset: the **Finance Transformation Blueprint
Accelerator** at `H:\My Drive\AA\blueprint-accelerator` (skill `03-boblueprint-accelerator`).
That repo owns the practice's vocabulary, the blueprint structure, and the house style — all of it
change-controlled and enforced in code. **Where this skill and that repo disagree, that repo wins.**

Read this before drafting anything a client will see.

---

## 1. "Blueprint" means two different things — do not blur them

| Term | What it is | Owned by |
|---|---|---|
| **Blueprint** *(practice definition — the default meaning)* | A single finance-transformation **use-case deliverable** in the house structure: narrative (3 paragraphs) → 4 pain points → 3 agents → user benefits per stakeholder (3 each) → 4 business benefits → checkpoint flags. Always this shape. | `blueprint-accelerator` — declared in `prompts/house_style_v1.txt`, enforced by `adapter/validation.py` |
| **EAEF blueprint** | The **implementation-ready engineering spec** generated by ICA Process Studio from an SOP: Atomic Thinking Step Register, Autonomy Zone Map, HITL Specification, Agent Definition Register, Data Products, Systems of Record, MCP Tools Catalog, Skills Library. | ICA Process Studio / the EA Engineering Framework — see skill `10-ica-process-studio` |
| **Target operating model (TOM)** | The **function-level architecture** produced by an assessment: seven layers from value proposition to performance management, covering the whole finance function. | This skill — `references/target-operating-model.md` |

**Three artifacts, one word.** They sit at different altitudes and are not interchangeable: the
TOM says what the function looks like, the house blueprint sells one use case to a client, and the
EAEF blueprint tells engineering what to build. Name which one you mean every time — a request to
"generate the blueprint" is ambiguous until you know whether the output is a client page or an
agent spec.

When someone in this practice says "blueprint", they mean the first one. This skill's Phase 1
produces the second, and calls it the target operating model everywhere. Say "target operating
model" or "TOM" when you mean the architecture; say "blueprint" only for the house artifact.

**How they connect** — this is the value of running the two together:

```
Assessment (this skill)                      Accelerator (03)
─────────────────────                        ────────────────
Phase 1  target operating model  ──────────▶ scopes which process areas need blueprints
Phase 2  benchmarks              ──────────▶ directional claims in business_benefits
Phase 3  pain point register     ──────────▶ the 4 pain points per use case (already
                                             evidenced, quantified and root-caused)
Phase 4  initiative backlog      ──────────▶ one blueprint per agentic initiative;
                                             waves set the drafting order
```

An assessment that ends without naming which use-case blueprints to draft has stopped one step
short. A blueprint drafted without an assessment behind it invents its own pain points.

## 2. The blueprint contract — counts are exact

Enforced twice: declared in the system prompt, validated by `validate_house_structure()`. A draft
that misses a count returns 422 and is retried; it is never silently accepted.

| Element | Requirement |
|---|---|
| `narrative` | Exactly **3** paragraphs, blank-line separated: current state → agents step in → end state. 3–5 sentences each. No bullets inside. |
| `pain_points` | Exactly **4** strings. Each: `<What is broken>. <What it costs.>` Unnumbered. Cover ≥3 distinct pain dimensions. |
| `agents` | Exactly **3** objects, each with `name`, `purpose`, `human_review`. Names are role names ("reconciliation agent"), never product names or "AI assistant". |
| `user_benefits` | Object keyed by stakeholder role; exactly **3** strings per role. Each starts with the verb the persona performs differently. |
| `business_benefits` | Exactly **4** strings, in this order: cycle acceleration · risk reduction · governance and auditability · scalability. Directional claims only — **no client-specific numbers**. |
| `checkpoint_flags` | Array of strings, no count constraint. First-class output, not commentary. |

**Never pad or invent content to hit a count.** If the input cannot support four pain points,
raise a checkpoint flag saying what is missing. This is the one rule most likely to be broken by a
model trying to be helpful.

**Never describe an agent that runs unattended on finance-sensitive content.** Every agent names
the human role that approves its output and the trigger that pauses for review. The cycle
acceleration comes from continuous visibility, not from removing the human.

## 3. Closed enums — do not invent members

**Process areas** (`R2R`, `OTC`, `ProjectAcct`, `Allocations`, `Inventory`, `Contracts`, `FA&IA`,
`PPAR`). A new member requires changes to the system prompt, the validator, the ICA prompt and the
benchmark scenarios in the same commit. Mapping from this skill's assessment taxonomy
(`target-operating-model.md` §2):

| Assessment taxonomy | Process area |
|---|---|
| B1–B6 Record and report | `R2R` |
| D1–D6 Sell and collect | `OTC` |
| A4 Cost and profitability management (allocation scope) | `Allocations` |
| A3 Management reporting, A5 business partnering | `FA&IA` |
| A1–A2 planning and forecasting (project/programme scope) | `PPAR` |
| Project accounting, WIP, project revenue recognition | `ProjectAcct` |
| Inventory and asset accounting | `Inventory` |
| Contract lifecycle, obligations, renewals | `Contracts` |

C (Source and pay), E (Treasury), F (Tax) and G (Payroll) have **no process area today**. Scope
falling there is assessed normally but cannot be drafted as a blueprint until the enum is extended
— raise it as a checkpoint flag rather than forcing it into the nearest member.

**The size of that gap is now measurable.** The golden thread spine
(`golden-threads.md`) holds 220 steps: all **59 Source-to-Pay steps** and the 7 RTR tax steps sit
outside the enum — roughly 30% of the built process spine cannot be drafted as blueprints. This is
the single largest structural gap between the two assets, and worth deciding deliberately rather
than discovering per engagement.

**Persona archetypes** (`Controller`, `GL Accountant`, `FP&A Analyst`, `Revenue Assurance Analyst`,
`Rebate Lead`, `Contract Lifecycle Manager`, `Order-to-Cash Lead`). Personas come from
`blueprint-accelerator/personas/inventory.yaml`, which is the source of truth for name, role and
archetype. A persona not in the inventory raises a `persona_flag` and is added only after senior
review. Never invent a persona silently, and never use a real client individual's name.

**Pain dimensions** (`cycle_time`, `control_risk`, `data_quality`, `decision_quality`,
`scalability`) — see §4.

## 4. Two pain taxonomies, and why both are needed

They are orthogonal, and the practice uses both:

- **Lens** (this skill — people / policy / process / data / technology) = **where the cause sits**.
  It determines what kind of intervention fixes it, so it drives the initiative and the roadmap.
- **Pain dimension** (the accelerator — cycle_time / control_risk / data_quality /
  decision_quality / scalability) = **what it costs the business**. It determines how the pain
  point is framed to the client, and the blueprint contract requires ≥3 distinct dimensions
  across the four pain points.

Record both on every register row. The columns exist in
`assets/pain-point-register-template.csv`. Worked example:

| Observation | Lens (cause) | Dimension (cost) |
|---|---|---|
| No-PO invoices need manual intervention | policy | cycle_time |
| Intercompany differences surface at day 5 of a 7-day close | process | control_risk |
| Three versions of revenue by region circulate | data | decision_quality |
| Reconciliations prepared in spreadsheets, reviewed by email | technology | control_risk |

**Selecting the four pain points for a blueprint:** take the highest `severity × frequency` rows
for that process area, then swap for dimensional coverage until at least three dimensions appear.
Four cycle-time pain points is a contract violation *and* a weak deliverable.

## 5. House style — voice rules that apply to everything

From `prompts/house_style_v1.txt`. These bind blueprints absolutely, and this skill's decks,
reports and proposals should follow them too.

- **Active voice. Present tense. Third person** — never second person.
- **Concrete and observable.** Not "there are some issues with X" but "manual capitalisation
  decisions create delays and misclassification risk."
- **Sentences average ~18 words, hard cap 28.** Vary length.
- **No filler hedges**: essentially, basically, really, very, just.
- **Banned marketing words** <!-- house-style: allow --> — *leverage, unlock, empower, seamless, robust, synergy,
  best-in-class, world-class, transformative*. Lint before delivery:

  ```
  python scripts/ft_house_style.py <file-or-directory>
  ```

  The only permitted appearance of a banned word is inside a cited proper noun (Hackett's
  "Digital World Class" is a defined benchmark cohort, not a claim about your client). The linter
  allows that one and flags everything else.
- **Process-first, not product-first.** No IBM product trade names unless they appear in the input.
- **No disclaimers, apologies, or meta-commentary about your capabilities.**

## 6. Checkpoint flags

The practice's governance mechanism, and it outranks this skill's `[SENIOR REVIEW]` marker
convention. Both exist for a reason:

- **Checkpoint flag** — a structured assumption, methodology, persona or SOX-control decision
  surfaced for human review. One sentence: *what you assumed* and *what you want confirmed*.
  It is an output field, not a note in the prose. Raise one for: an assumption made because the
  input was silent · a methodology choice where sources conflict · a persona not in the inventory ·
  a SOX-relevant control decision made on the agent's behalf · a claim depending on a number not
  visible in the input.
- **`[SENIOR REVIEW]` marker** — an in-document placeholder where a deck or report page lacks
  content. Used in narrative deliverables where there is no structured flag field.

Rule of thumb: if the deliverable has a `checkpoint_flags` field, use it. If it is a deck or a
document, use the marker and list every one at handover. Never invent content to fill either.

**No SOX-relevant content reaches a client without senior consultant sign-off.** Nothing in this
skill auto-approves.

## 7. The ~45% collision — two different numbers, same digits

Both appear in this practice's material and they are unrelated. Conflating them would be a serious
credibility failure in front of a CFO:

| "~45%" | What it measures | Where it belongs |
|---|---|---|
| **IBM Bob benchmark** | Approximate first-draft cycle-time reduction observed across the internal Bob user base. An internal productivity figure. | The accelerator's submission one-pager, demo script and slide 8 |
| **Hackett Digital World Class** | Digital World Class finance organisations operate at ~45% lower cost as a percentage of revenue than their peer group (June 2025). An external cost benchmark. | `benchmark-library.md` §2, client benchmark pages |

Never cite one as evidence for the other. When the accelerator's IBM benchmark changes, AGENTS.md
requires updating the one-pager and demo script — search for `~45%` in the accelerator repo, and
check nothing in a client deck picked up the wrong one.

## 8. Hard constraints inherited from the accelerator repo

1. **No client data** in the accelerator repo, ever. Personas fabricated, SOWs and interview notes
   synthetic. Client data stays in the engagement repo.
2. **House structure changes require a version bump** (`house_style_vN.txt`) with the prompt and
   the validator updated in the same commit. Do not "just adjust" a count.
3. **Fail closed.** Malformed input or a schema validation failure returns a tagged error, never a
   degraded result.
4. **Blueprints are process-first.** No product trade names unless supplied in the input.
